# Background CPU investigation — 6 October 2026

The starting release is `70e7c4a`. The user requested lower CPU use after a
three-minute comparison measured upstream 1.14.0 at 0.09549% of one logical core
and the running Rust release at 0.11285%. This was not a controlled speed test:
upstream had one simulated mouse, no hardware polling and no animation; Rust
monitored real devices with its existing settings. Both had status export off.
The difference was only 31.25 ms of processor time over 180 seconds, so one run
does not establish a statistically significant regression or its precise cause.

## Investigation and changes

A separate three-minute sample of the running Rust process attributed 140.625 ms
to its main/UI thread, 15.625 ms to each of the state, two HID and WinRT workers,
and no measurable time to storage. These Windows counters have coarse resolution
at this scale. This points to the tray path as an important investigation target;
it is not a sampled call-stack profile proving where each CPU tick was spent.

- **Dock detection:** automatic tray appearance enumerated all running processes
  every ten seconds even without MyDockFinder. Absent-dock checks now have a
  thirty-second cache; the ten-second cadence remains while a dock is present.
  Explicit appearance changes, Windows theme notifications and Explorer recovery
  bypass the cache. A newly started dock without a corresponding theme event can
  therefore take up to thirty seconds to affect icon colours. Executable names
  are compared directly as UTF-16, eliminating per-process string allocations.
- **HID discovery:** each vendor metadata refresh separately scanned all Windows
  HID interfaces. A one-second census now shares counts between different vendors
  in a polling burst. Connection generations invalidate it immediately. Repeated
  queries for the same vendor deliberately scan again so incomplete-collection
  and failed-open recovery retain their immediate retry. Errors never become
  successful empty inventories. HIDAPI still performs vendor-specific discovery;
  missing or unusual census paths do not prevent a device from being queried.

No battery refresh interval, gaming-state restriction, report, tray animation
cadence, history retention or provider allowlist changed. No new background
thread, timer or dependency was added. The user's normal process and settings
were left running unchanged.

## Targeted measurement

The read-only discovery example performs seven full refresh bursts across the
23 unique battery-catalog vendors. It sends no battery or configuration reports.
All seven rounds found 15 collections both before and after the change.

| Metric | Starting implementation | Updated implementation |
|---|---:|---:|
| Complete HID census scans per uninterrupted burst | 23 | 1 |
| Median discovery elapsed time | 112.38 ms | 107.56 ms |
| Total processor time over seven rounds | 125 ms | 62.5 ms |
| Absent-dock scans per three minutes at five-second heartbeats | 18 | 6 |

The discovery timing includes vendor-specific HIDAPI work, which is retained.
These are short component measurements with quantized CPU counters, not a claim
that overall application CPU has halved. The scan-count reduction is covered by
deterministic tests; elapsed/CPU timings depend on the machine and devices.

Reproduce discovery timings with a release build of
`cargo build -p hb-windows --example measure_discovery --release --locked`, then
pass the catalog's distinct hexadecimal vendor IDs to the example executable.
It reports aggregate counts/timings only, not hardware identities or names.

## Validation

Formatting, strict workspace Clippy, 593 tests, the frozen 459-ID upstream mapping
gate and the portable release build pass. Two optional SQL timing tests remain
excluded. Regression tests cover census reuse, expiry, reconnect generations,
same-vendor retries, errors, clock regression, absent/present dock caching,
explicit theme refresh and Unicode process-name matching.

The updated native fixture also passed forty dashboard open/close cycles without
growing its GDI/USER handle counts. It measured 0.04340% of one core and 6.32 MiB
average private memory before those cycles, then 0.09545% and 6.50 MiB afterward,
in separate 180-second windows. Both had a closed dashboard, a simulated mouse,
no charging animation and screenshot capture disabled. These are two lifecycle
phases, not two implementations; the difference shows why one low-CPU window
should not be treated as a precise universal performance figure.

The release is 3,072,512 bytes (2.93 MiB), SHA256
`3B5A552A1AF65DBE095721850E0CA2C1D813C2DEBD61F3082964D715FD8774D8`.
Production import restrictions and source/executable privacy checks pass.

## Matched native fixture comparison

An unchanged `70e7c4a` source archive was built with the same optimized test
profile and compiler. Both builds ran the same native lifecycle fixture with
screenshot capture off and the user's normal app still running alongside it.
The baseline's only harness adjustment permits selecting the first measurement
phase; it changes neither production behavior nor that measurement loop. Each
measurement below precedes the forty-cycle stress sequence.

| Three-minute native simulation | Unchanged `70e7c4a` | Updated |
|---|---:|---:|
| Duration | 180.05 s | 180.03 s |
| CPU, one logical core | 0.16488% | 0.04340% |
| Average private memory | 6.30 MiB | 6.32 MiB |
| Peak private memory | 14.14 MiB | 14.20 MiB |

That window used approximately 74% less CPU with essentially unchanged memory.
The additional updated window after forty dashboard cycles measured 0.09545%,
so the first-window reduction is not a promise of a constant 74% improvement.
These simulated fixtures bypass provider I/O: the difference supports the tray
work savings, while the separate read-only discovery benchmark covers HID census
work. They are not a new matched comparison against upstream Python or a claim
that production hardware CPU is already below its earlier 0.09549% reading.

To select one measurement phase, build the native tests in release mode, set
`HALO_MEASURE_UI_RESOURCES=before-40-cycles`, and run
`ui::dashboard_lifecycle_tests::native_dashboard_reopens_after_nested_close_and_external_destruction`
with `--exact --nocapture --test-threads=1`. Value `1` measures both phases;
`after-40-cycles` selects the second. The test executable is a Windows GUI binary;
use `Start-Process -WindowStyle Hidden -Wait` to wait for completion reliably.

A production before/after hardware comparison requires restarting the normal
app; it was not restarted for this audit.
