# Consumer UI audit — 5 October 2026

The dashboard and tray menus now share a quieter native Windows design. This
pass prioritizes legibility, understandable controls and minimal background work.
Existing hardware protocols and polling safeguards are unchanged.

## Resource design

The app still uses Win32 controls, GDI and an on-demand Direct2D History target.
There are no new dependencies, webviews, background workers, polling queries,
UI animation timers, bitmap caches or backdrop effects. Two fonts and two theme
brushes are reused while the dashboard is open. Rounded drawing uses Windows'
stock pen/brush. A small per-control state remembers the palette, control type and
hover boundary; moving within a hovered button does not request another repaint.
One native page scrollbar exists only with scrollable dashboard pages.

Closing the dashboard releases its controls, fonts, theme brushes, scrollbar,
History target and loaded Insights. The 40-cycle native regression checks that
closed-window GDI/USER handles do not grow. The resource fixture uses optimized
Rust code and invented data, and runs a three-minute closed-dashboard sample on
each side of 40 open/close cycles. It does not establish physical-device memory
or CPU, and is not a fresh comparison against the original Python application.

## Validation and limits

Native regressions exercise light/dark and high-contrast controls, selected text,
hover invalidation, actual scrollbar message routing, retained edits, small-window
scrolling, fixed footers, page changes and cleanup. Existing keyboard behavior is
preserved; new keyboard features were not part of this request.

[Screenshots](screenshots/README.md) use the actual native renderer and invented
readings. Both themes and expanded Settings were visually inspected. History
uses the application's Direct2D renderer with a synthetic two-hour discharge.
No user settings or Windows appearance preferences were changed, and the running
monitor was not replaced. No physical device commands or new hardware verification
were performed. Manual inspection on multiple monitors and touch interaction were
not performed.

The first resource attempt was discarded: its test-only wait loop watched all
thread messages but consumed only monitor messages, leaving other queued messages
to wake it repeatedly. The corrected fixture drains the full thread queue. The
production application uses GetMessage and did not contain this test-loop defect.

## Scrollbar follow-up — 6 October 2026

The themed page scrollbar could flicker because native range updates and mouse
tracking painted directly underneath its custom surface. The page also overlapped
the scrollbar's sibling window. The page now reserves a separate scrollbar strip,
with matching DPI rounding, and skips unchanged range/position updates.

The light/dark scrollbar handles dragging and held clicks without entering the
native direct-paint tracking loop. Its range remains in the standard Windows
control; high contrast retains native input and drawing. The themed thumb is
calculated from the current range, rather than native paint's cached geometry.
Its repeat timer exists only during a held click and is cancelled on release,
capture loss, cancellation, a high-contrast transition or destruction. No worker,
idle timer, bitmap cache or background monitoring was added.

All 570 workspace tests pass (two optional timing tests ignored), along with
formatting and strict Clippy. Native checks cover deferred themed rendering,
idle mouse movement without redraw, arrow clicks, thumb dragging, cancellation,
nonoverlapping page bounds and unchanged-position redraw suppression. Forty
open/close cycles retain the same closed-window GDI/USER counts (21/22).
Synthetic captures were inspected in both themes. This follow-up does not repeat
the three-minute resource measurements above or claim manual hardware validation.
