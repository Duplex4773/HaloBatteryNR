# Logitech polling-rate protocol evidence

This is an independent Rust implementation of the HID++ wire facts described below. Only explicit user requests invoke it. Discovery sends getter packets over the HID++ output channel; it never changes a setting. No mouse commands were sent to physical hardware while implementing or testing this feature.

## Scope and primary sources

- [Solaar feature implementation](https://github.com/pwr-Solaar/Solaar/blob/e7304c4c451cc9bb4f206a914844525e67856a28/lib/logitech_receiver/settings_templates.py): `ExtendedReportRate` uses feature `8061`, capability function `10`, getter `20`, setter `30`. The capability mask is a big-endian 16-bit integer. Seven code values 0–6 represent 125, 250, 500, 1000, 2000, 4000, 8000 Hz. Function numbers are the upper nibble of the HID++ function/software-ID byte.
- [Solaar identity decoder](https://github.com/pwr-Solaar/Solaar/blob/e7304c4c451cc9bb4f206a914844525e67856a28/lib/logitech_receiver/hidpp20.py): feature `0003` function zero supplies the four-byte unit at payload offsets 1–4, transport flags at offset 6, and packed two-byte transport IDs at offsets 7–12. Transport flags are Bluetooth, BLE, wireless PID, USB PID in that order.
- [Published PRO X 2 hardware feature listing](https://github.com/pwr-Solaar/Solaar/blob/e7304c4c451cc9bb4f206a914844525e67856a28/docs/devices/PRO%20X%202%2040A9.text): mouse model IDs `40A9`/`C09B`, receiver `C54D`, feature `8061` and onboard profiles `8100`.
- [DEX hardware report, Solaar issue 2904](https://github.com/pwr-Solaar/Solaar/issues/2904): model IDs `40B8`/`C0A0`, receiver `C54D`, feature `8061`. The report also demonstrates that a stored/configured 8000 Hz value is not sufficient evidence of an effective 8000 Hz reporting rate.
- [DEX wired report, Solaar issue 2836](https://github.com/pwr-Solaar/Solaar/issues/2836): corroborates direct `C0A0` and the `40B8/C0A0` pair. It does not establish a `C53A` route or an 8000 Hz receiver ceiling; the earlier receiver attribution was incorrect.
- [Superstrike feature listing](https://github.com/pwr-Solaar/Solaar/blob/e7304c4c451cc9bb4f206a914844525e67856a28/docs/devices/PRO%20X%202%20Superstrike%2040BD.txt): exact `40BD/C0A8` pair, `8061` V0 and `8100` V0. [Solaar issue 3202](https://github.com/pwr-Solaar/Solaar/issues/3202) corroborates this model on receiver `C54D`.
- [Logitech Superstrike settings](https://www.logitechg.com/en-ph/discover/learn/superstrike-g-hub-settings): manufacturer specifies up to 8000 Hz wireless. [Logitech pro settings](https://www.logitechg.com/en-au/discover/learn/superstrike-hits-codes) distinguish 1000 Hz wired settings from higher wireless settings. This implementation conservatively caps direct USB at 1000 Hz.
- [Logitech PRO LIGHTSPEED receiver](https://www.logitechg.com/en-za/shop/p/pro-lightspeed-receiver): specifies up to 8000 Hz and compatibility with Superlight 2, DEX and Superstrike. This marketing page does not establish any additional receiver USB PID.
- [OpenMouse live report-rate implementation](https://github.com/OpenMouse-Project/mouse-protocol/blob/beef2df996836dbc6a488b8c2e38a67603ec6102/src/drivers/logitech/hidpp.ts): independently corroborates the feature, functions, big-endian mask and indexed rate values. It distinguishes a configured getter value from a live rate-change notification.
- [OpenMouse hardware captures and connection limits](https://github.com/OpenMouse-Project/mouse-protocol/blob/beef2df996836dbc6a488b8c2e38a67603ec6102/docs/logitech-onboard-profiles.md): Superlight 2 wireless polling reaches 8000 Hz; wired charging connection is limited to 1000 Hz. Published profile captures corroborate the indexed rate representation. This implementation does **not** copy or implement profile-sector rewrites.

The initial sources were inspected on 2026-09-30; the expansion sources were inspected on 2026-10-01. Solaar source is GPL-2.0-or-later. OpenMouse's inspected snapshot did not provide a repository license file or package license declaration. No implementation, comments, profile encoder or source tests from either project are copied here. The packet construction, matching loop, routing guard and synthetic regressions were written independently from the protocol facts. No GPL dependency is linked or distributed. User unit IDs and receiver serials from published reports are deliberately omitted from this document and synthetic fixtures use invented identifiers.

## Target and mode checks

Only Logitech vendor `046D`, long HID++ collection `FF00:0002`, receivers `C54D`/`C53A`, and direct USB models `C09B`/`C0A0`/`C0A8` are considered. A receiver PID never proves which paired mouse is present. Every candidate slot must return the selected reading's nonzero eight-hex-digit hardware unit and one of the exact `40A9/C09B`, `40B8/C0A0` or `40BD/C0A8` pairs. Names and positional matching are never used. A direct connection must also match the model's USB PID. Superstrike is refused on `C53A` because no inspected source corroborates that pairing. This scope does not imply support for other Logitech devices exposing the same feature.

The 2026-10-01 audit adds one model, PRO X2 SUPERSTRIKE, already discoverable by the battery provider through the known `C54D` receiver or direct HID++. It adds no generic unknown-PID control path. Current route ceilings are:

| Exact model pair | C54D receiver | C53A legacy route | Direct USB |
| --- | --- | --- | --- |
| Superlight 2 `40A9/C09B` | 8000 Hz | 1000 Hz conservative cap | 1000 Hz |
| Superlight 2 DEX `40B8/C0A0` | 8000 Hz | 1000 Hz conservative cap | 1000 Hz |
| Superstrike `40BD/C0A8` | 8000 Hz | Refused | 1000 Hz conservative cap |

Every ceiling is intersected with the mouse's advertised mask. The retained `C53A` route offers only legacy rates; its earlier unproven 8000 Hz advertisement is removed. Receiver pairing capability alone does not prove report-rate capability. Other receivers, SE/2c variants and PRO 2 remain unsupported by controls until their exact model pair, transport route and protocol are corroborated. [Open libratbag PR 1896](https://github.com/libratbag/libratbag/pull/1896) describes additional models and per-connection queries, but an unmerged implementation is not treated as proof that generic receivers or wired connections support 8000 Hz.

The adapter enumerates fresh groups, matches an independently recorded container when supplied, and requires exactly one proven unit route. Unknown/unresolved routes, duplicate slots/collections/routes, stale enumeration epochs and slot-only fallback reading keys refuse a SET. Long and short sessions are guarded before and after every transport operation. Identity and capabilities are re-read immediately before a SET.

Only advertised rates within the route ceiling above are offered. If a valid software getter code lies outside the current connection capability list, it is informational only: no restorable previous value is returned and a SET is refused. Feature `8100` function `20` reports mode: 1 is onboard profile mode; 2 is software control mode. Solaar's onboard-profile reader and setter explicitly use these values. An onboard or unknown mode refuses changes and does not automatically switch profiles, disable profiles, modify DPI/buttons, or rewrite flash. The UI can explain that software control mode in G HUB is required.

A Read in onboard/unknown mode retains the capability list and explains the software getter value but returns no verified current rate or restorable previous rate. A software-mode result represents **configured rate readback**, not an independent measurement of effective USB/receiver polling frequency. No physical behavior is claimed validated locally.

This qualification is particularly relevant to Superstrike: the author's [empirical device notes](https://github.com/mclol0/linux-superstrike/blob/main/REVERSE_ENGINEERING.md) report cached getters. Those observations do not validate this software-mode transaction locally. The app does not implement that project's onboard-memory workaround or measure pointer reports, and a matching getter is not claimed to establish the effective report frequency. Normal user-mode HID output/read operations are the entire control boundary: no process hooks, injection, game-memory reads, drivers, input emulation or anti-cheat interaction are used.

## Exchanges and failure handling

Twenty-byte long output packets carry report ID `11`, slot, discovered feature index, function/software ID and zero-padded parameters. Replies match slot, feature and the full software-ID byte. Foreign/late tokens are ignored on both long and short channels; matching HID++ 1/2 errors are surfaced. Matching malformed long frames fail rather than guessing their offsets. Requests are bounded to 600 ms and the caller's cancellation/deadline.

A SET uses only feature `8061` function 3 and one indexed-rate byte. No hidden enforcement loop exists. A fresh getter follows the attempt, including transport/acknowledgment failures where the mouse might have changed. Such outcomes retain their failure even if readback matches. The getter is followed by another read of feature `8100` function 2. A concurrent switch to onboard mode, an unknown mode or a failed mode query suppresses the active-rate claim and restorable previous value; any earlier partial failure is retained. This extra query never writes profiles or changes control mode. Mismatched or unknown readback is not success. `may_have_changed` explicitly signals uncertainty after a SET attempt; restoration uses a separate, explicitly requested transaction and must revalidate identity again.

## Verification

`cargo test -p hb-providers --test logitech_controls --test provider_logitech_io` passed 26 control regressions and 21 provider I/O regressions on 2026-10-01 using synthetic strict sessions only. Regressions cover all three exact model pairs, Superstrike receiver SET/readback and direct adapter routing, refusal of its unproven C53A route, conservative C53A/wired limits, advertised-mask changes, unsupported targets, exact unit validation, nonfirst paired slot, foreign/late replies, both error channels, malformed frames, empty/unknown capabilities, software/onboard/unknown modes, no-op/read-only requests, wrong identity after pairing changes, duplicate receiver routes, exact-container checks, epoch changes, SET failure with successful readback, mismatch/unknown readback, cancellation and 600 ms timeout. Expected packets include complete zero padding; extra or missing operations fail.

Local physical validation of discovery, accepted SETs, effective polling frequency and restoration remains pending the user's separately authorized hardware session. No hardware tests are inferred from the synthetic suite or the reference projects' captures.
